# Opus LaneSight presentation script

## Positioning

**Product:** Opus LaneSight

**Use case:** Publish clear, current inspection-station wait-time estimates from standard camera footage.

**Audience:** Opus operations, agency stakeholders, AWS hackathon judges, and product/engineering reviewers.

**Status:** Working prototype: local desktop/CLI video analytics, deterministic station metrics, AWS serverless snapshot API, and static public wait-time dashboard.

---

## Slide 1 — Title

# Opus LaneSight
## Inspection-station wait-time intelligence from standard camera footage

**Speaker notes**

Opus LaneSight is a prototype that turns ordinary station camera footage into anonymous wait-time metrics. The goal is not to identify drivers. The goal is to understand station flow well enough to show motorists a useful public wait estimate and give operators a clearer view of queue conditions.

---

## Slide 2 — The problem

# Wait-time visibility matters

- Motorists want to know when to visit an inspection station.
- Station teams need visibility into queues, throughput, and delays.
- Specialized instrumentation can be expensive to expand station by station.
- Plate-based systems are useful, but they are not always necessary for aggregate wait-time estimates.
- Public-facing tools should avoid exposing internal model details or driver identity.

**Speaker notes**

Inspection programs already care deeply about wait time. The challenge is getting timely and trustworthy station-level information without requiring every wait-time use case to depend on identity capture or specialized hardware. LaneSight explores whether existing camera footage can produce useful operational signals in a lower-friction way.

---

## Slide 3 — The prototype

# What LaneSight does today

- Accepts MP4 files or RTSP/RTMP/HTTP camera streams.
- Detects vehicles with local YOLOv8 or optional Amazon Rekognition.
- Tracks anonymous vehicle session IDs through the scene.
- Computes wait-time and station-level metrics from observed tracks.
- Publishes the latest station snapshot to a serverless API when configured.
- Displays a public wait-time card in a static web dashboard.

**Speaker notes**

This is a working end-to-end slice. We can process video locally, calculate metrics, publish a snapshot through an HTTPS API, store the current station state in DynamoDB, and show that state on a browser-based public dashboard.

---

## Slide 4 — Current architecture

```text
Video file or live stream
        |
        v
Vehicle detector
  YOLOv8 locally or Rekognition in AWS
        |
        v
Tracker
  Kalman prediction + assignment + appearance re-ID
        |
        v
Station metrics
  queue-depth proxy + active lanes + observed cycle time
        |
        +--> Desktop/CLI results
        |
        v
Station Stats API
  API Gateway + Lambda + DynamoDB
        |
        v
Public dashboard
  Static HTML/CSS/JavaScript
```

**Speaker notes**

The architecture is intentionally simple. Video processing runs locally in the prototype. The serverless API stores the latest metric snapshot per station. The public dashboard only reads the latest approved snapshot and presents it in a motorist-friendly way.

## Slide 5 — Demo flow

# End-to-end demo

1. Set a station identifier and display name.
2. Process a station video or stream in the desktop app.
3. Review detected vehicles and calculated station metrics.
4. Publish the latest station metric snapshot.
5. Open the public dashboard and select the station.
6. Show wait estimate, status, open lanes, and last-updated time.

**Speaker notes**

For the demo, the operator starts with a known station identity. LaneSight processes the footage, tracks vehicles, calculates the current station metrics, and publishes a compact JSON snapshot. The public page then renders a clean card for motorists. It does not show raw detections, confidence scores, model internals, plate numbers, or driver information.

---

## Slide 6 — Wait-time calculation

# Transparent formula

```text
estimated_public_wait_minutes = queue_depth * average_inspection_minutes / active_lanes
```

Current prototype inputs:

- `queue_depth`: peak concurrent tracked vehicles in the observed window.
- `average_inspection_minutes`: average observed vehicle cycle duration.
- `active_lanes`: operator-configured station setting.

**Speaker notes**

The wait estimate is deterministic. It is not generated by a language model. In the current prototype, we do not yet have calibrated lane and zone polygons, so queue depth is a proxy from the tracked scene and active lanes are configured by the operator. That makes the calculation explainable and honest about its current limits.

## Slide 7 — Public dashboard use case

# Motorist-friendly station wait card

The public dashboard shows:

- available stations with current snapshots;
- a rounded wait estimate in minutes;
- plain-language status: normal wait, moderate wait, or queue building;
- open lanes;
- last-updated time;
- graceful unavailable states when data is missing or low confidence.

**Speaker notes**

The public use case is intentionally narrow. A motorist should be able to choose a station and quickly understand whether now is a good time to visit. The page hides operational internals and falls back safely when the estimate should not be shown.

---

## Slide 8 — Operator use case

# Station and program operations

LaneSight can support operators by surfacing:

- total tracked vehicles;
- completed vehicles;
- peak concurrent vehicles;
- average observed wait/cycle duration;
- throughput per hour;
- current public wait estimate;
- station identifier attached to every published snapshot.

**Speaker notes**

The operator view is useful for demo and pilot conversations because it connects raw video analysis to station-level business metrics. It gives teams a concrete artifact to compare against existing wait-time methods and manual observations.

## Slide 9 — Privacy posture

# Privacy-preserving by default for public wait times

- Temporary anonymous vehicle IDs are used for tracking.
- OCR is optional and should remain disabled for public wait-time demos and pilots.
- Public output is aggregate station information only.
- The API stores the current metric snapshot, not video frames or vehicle images.
- The dashboard avoids internal model terms and vehicle-level details.

**Speaker notes**

LaneSight separates wait-time measurement from identity. The codebase includes OCR utilities for experimentation, but the intended public workflow does not need plate reading. For public-facing scenarios, the message is simple: aggregate wait-time information, not driver identification.

## Slide 10 — AWS components

# AWS deployment slice

Implemented in the repository:

- **API Gateway** for HTTPS endpoints.
- **Lambda** for snapshot writes, station reads, list reads, and credential authorization.
- **DynamoDB** for the latest snapshot per station.
- **SAM template** for repeatable deployment.

Optional in the analytics pipeline:

- **Amazon Rekognition** as a cloud vehicle-detection backend.

Future opportunities:

- Secrets Manager or SSM Parameter Store for credentials.
- CloudFront for the public dashboard.
- Bedrock for grounded operations summaries based only on measured metrics.

**Speaker notes**

The current AWS slice is focused and deployable. It stores current station state and serves it over a controlled API. Rekognition is optional for detection. Bedrock is not part of the current implementation, but it is a logical next step for operator summaries once the underlying metrics are validated.

## Slide 11 — Deployment story

# How this can be deployed for a demo

1. Deploy `infra/template.yaml` with AWS SAM.
2. Configure a demo or pilot client credential.
3. Capture the API Gateway `ApiBaseUrl` output.
4. Configure the desktop app with the API URL and credential.
5. Configure `src/config.js` for the public dashboard.
6. Host `src/` with S3 and CloudFront, or run it locally for a demo.

**Speaker notes**

Deployment is intentionally lightweight. The API is serverless. The public dashboard has no build step. For a real public deployment, the dashboard credential model should be replaced with a server-side or edge proxy so write-capable credentials are not exposed in browser JavaScript.

**Speaker notes**

This slide is important because it sets accurate expectations. LaneSight is a credible prototype, not a finished production platform. The value is that the thin slice is real and testable, and the next steps are clear.
